# performance_dashboard 验证与实现文案

本文档只用于前端“验证与实现”窗口展示。内容按性能验收视角组织，聚焦指标阈值、真实压测路径、关键统计字段和可复查结果证据。

## performance/PF-1 RDMA 网络环境分布式通讯能力

### 验证目标
性能要求：分布式的带宽利用率达到 50% 以上，单个对象 1KB 时吞吐量达到 100 万/s。

- 验证 1KB 小对象跨节点通信吞吐达到 1,000,000 ops/s。
- 验证大对象 RDMA peer 复制路径的网络带宽利用率达到 50%。
- 验证失败数、降级数、成功率和网络发送带宽均可从结果中复查。

### 实现方案
- 性能脚本调用 C++ 压测二进制 `nr_bench`，通过 UDS 进入 C++ 数据面热路径。
- 小对象场景统计成功对象操作数和 measured 时间，带宽场景采集数据面 shared-memory metrics 中的 RDMA TX 带宽。
- 数据面要求 peer 在线，避免本地 degraded 路径被计入达标结果。
- 页面只展示验收文案、结果摘要和原始结果，基线证据来自 `performances/PF-1/summary.md` 与 `raw.json`。

### 测试方案

前置条件：
- 双节点 C++ 数据面在线，UDS 可访问。
- RDMA peer 已连接，OOB 元数据交换完成。
- `nr_bench` 可执行文件已构建。
- 数据面 metrics shared memory 可读取。

测试方案：
- 执行 1KB 小对象吞吐压测，检查 `ops_per_sec`、失败数和降级数。
- 执行大对象带宽压测，采集 `bw_tx_gbps` 并计算链路利用率。
- 检查两个子项均通过，且失败数、降级数为 0。
- 检查 `summary.md` 和 `raw.json` 中的阈值、吞吐、带宽和判定字段。

## performance/PF-2 RDMA 网络环境下对象传输能力

### 验证目标
性能要求：端到端传输 10 万个仿真对象，单个对象 1KB 时，数据平均时延不超过 50 微秒，P99 响应时间不超过 100 微秒。

- 验证 1KB 对象传输的平均时延满足阈值。
- 验证 P99 响应时间满足阈值，并保留 P50、P99.9 和最大值。
- 验证成功样本数、失败数和降级数可复查。

### 实现方案
- 性能脚本调用 `nr_bench` 进入 C++ 数据面，执行 1KB 对象 mixed workload。
- 压测过程丢弃 warmup，只统计 measured 窗口内成功样本的端到端数据面时延。
- `raw.json` 保存平均值、分位数、最大值、样本数、失败数和降级数。
- 页面展示时延指标和结果材料，不把控制面页面操作时间计入性能结果。

### 测试方案

前置条件：
- 双节点 C++ 数据面在线，UDS 可访问。
- RDMA peer 在线，传输路径未降级。
- `nr_bench` 可执行文件已构建。

测试方案：
- 执行 1KB 对象传输时延压测，采集成功样本。
- 计算平均时延、P50、P99、P99.9 和最大时延。
- 检查平均时延不超过 50 微秒，P99 不超过 100 微秒。
- 检查失败数和降级数未污染成功样本。
- 检查 `summary.md` 和 `raw.json` 中的分位数与阈值判定。

## performance/PF-3 RDMA 网络环境下 QoS 事件优先级传输能力

### 验证目标
性能要求：高优先级事件 2500 个、低优先级事件 2500 个，高优先级比低优先级处理效率提升 22%。

- 验证高低优先级事件在同一竞争窗口内分别完成统计。
- 验证高优先级处理效率相对低优先级提升达到 22%。
- 验证 QoS 模式、失败数、降级数和 P99 时延可复查。

### 实现方案
- `nr_bench` 分别以高优先级和低优先级请求进入同一个 C++ 数据面。
- C++ 数据面 `QosSched` 使用高低优先级 QP 分组和低优先级保护机制。
- 性能脚本统计 `hi_ops`、`lo_ops`，并计算 `gain_pct`。
- 结果材料保留 QoS 配置、吞吐、分位数、失败数和降级数。

### 测试方案

前置条件：
- 双节点 C++ 数据面在线，UDS 可访问。
- RDMA peer 在线，QoS 调度器已初始化。
- `nr_bench` 可执行文件已构建。

测试方案：
- 同时提交高优先级和低优先级事件流。
- 分别统计高优先级和低优先级事件完成吞吐。
- 按 `(hi_ops - lo_ops) / lo_ops * 100%` 计算提升比例。
- 检查提升比例不低于 22%，且失败数、降级数符合验收要求。
- 检查 `summary.md` 和 `raw.json` 中的 QoS 模式、吞吐和判定字段。

## performance/PF-4 RDMA 网络环境下对象数据聚合传输能力

### 验证目标
性能要求：100 个 1KB 仿真对象 1000 批次传输总耗时不超过 200ms；1000 个 1KB 仿真对象 100 批次传输总耗时不超过 100ms。

- 验证两个批量聚合场景的总耗时分别满足阈值。
- 验证每个场景的成功批次数、失败批次数和降级批次数可复查。
- 验证计时覆盖从第一批提交到最后一批完成确认的 measured 窗口。

### 实现方案
- 性能脚本调用 `nr_bench` 进入 C++ 数据面批量传输路径。
- 场景 A 和场景 B 分别执行，按批次完成时间计算总耗时。
- 数据面要求 peer 在线，批量传输不能使用本地降级结果冒充达标。
- 结果材料按场景保存 elapsed、批次数、对象数和通过判定。

### 测试方案

前置条件：
- 双节点 C++ 数据面在线，UDS 可访问。
- RDMA peer 在线，批处理路径可用。
- `nr_bench` 可执行文件已构建。

测试方案：
- 执行 100 对象乘 1000 批次场景，检查总耗时不超过 200ms。
- 执行 1000 对象乘 100 批次场景，检查总耗时不超过 100ms。
- 检查成功批次数、失败批次数和降级批次数。
- 检查 `summary.md` 和 `raw.json` 中两个场景的明细和总体判定。

## performance/PF-5 RDMA 网络环境下批处理能力

### 验证目标
性能要求：仿真引擎单个对象 1KB 时，批处理传输速度不低于 700MB/s。

- 验证批处理业务载荷吞吐达到 700MB/s。
- 验证对象操作吞吐、成功字节数、失败数和降级数可复查。
- 验证 1000 批次和 100 批次场景都进入同一批处理性能口径。

### 实现方案
- 性能脚本调用 `nr_bench` 压测 C++ 数据面批量对象传输路径。
- 吞吐按成功业务载荷字节数除以 measured 时间计算。
- `raw.json` 保存 `mb_per_sec`、`ops_per_sec`、对象大小、失败数和降级数。
- 页面展示批处理性能结果，不展示脚本内容或运行命令。

### 测试方案

前置条件：
- 双节点 C++ 数据面在线，UDS 可访问。
- RDMA peer 在线，批处理传输未降级。
- `nr_bench` 可执行文件已构建。

测试方案：
- 执行 1KB 对象批处理压测，采集 measured 窗口内成功对象数和字节数。
- 计算 `mb_per_sec` 和 `ops_per_sec`。
- 检查批处理吞吐不低于 700MB/s。
- 检查失败数、降级数和 fallback 情况。
- 检查 `summary.md` 和 `raw.json` 中的吞吐和判定字段。

## performance/PF-6 多级存储读写能力

### 验证目标
性能要求：实现数据写入速率达到 10GB/s，数据读取速率达到 20GB/s。

- 验证多级存储写入吞吐不低于 10GB/s。
- 验证读取吞吐不低于 20GB/s。
- 验证读写吞吐按真实成功字节数统计，避免用估算值冒充结果。

### 实现方案
- 性能脚本调用 `nr_bench` 进入 C++ 数据面对象读写路径。
- 写入吞吐使用真实成功写入字节数和 measured 时间计算。
- 读取吞吐使用真实响应字节数、命中率、miss 和短响应字段计算。
- 结果材料保留读写 GB/s、命中率、失败数、降级数和环境说明。

### 测试方案

前置条件：
- C++ 数据面在线，UDS 可访问。
- 目标存储路径和层级配置可用。
- 大对象场景需要数据面 slab slot 足够容纳测试 payload。
- `nr_bench` 可执行文件已构建。

测试方案：
- 执行写入吞吐压测，按成功写入字节数计算 `write_gbs`。
- 执行读取吞吐压测，按真实响应字节数计算 `read_gbs`。
- 检查写入不低于 10GB/s，读取不低于 20GB/s。
- 检查读 miss、短响应、失败数和降级数。
- 检查 `summary.md` 和 `raw.json` 中的读写吞吐、命中率和判定字段。

## performance/PF-7 仿真引擎定期备份存储能力

### 验证目标
性能要求：3+1 RAID5 系统下的 4KB 请求写入 P999 延迟不超过 1ms。

- 验证备份写入路径的 P999 延迟满足 1ms 阈值。
- 验证 RAID5 ready、后端类型、请求大小和失败写入数可复查。
- 验证 P50、P95、P99、P999、最大延迟均保留在结果中。

### 实现方案
- 默认性能路径通过数据面 `RPC_BACKUP_WRITE` 执行 4KB 备份写入。
- 数据面备份写入独立于普通热路径，避免影响 RDMA 小对象吞吐和端到端时延。
- 如使用 fio 后端，结果中以 backend 字段标注为存储设备对照路径。
- 结果材料保存延迟分位数、成功写入数、失败写入数、RAID5 ready 状态和测试路径。

### 测试方案

前置条件：
- 备份测试路径可写，并具备 RAID5 ready 能力。
- 数据面备份 RPC 或 fio 后端可用。
- 测试路径容量满足短时 4KB 写入压测。

测试方案：
- 执行 4KB 备份写入压测，采集成功写入延迟样本。
- 计算 P50、P95、P99、P999 和最大延迟。
- 检查 P999 不超过 1000 微秒，且失败写入数为 0。
- 检查 RAID5 ready 字段、backend 字段、测试路径和展示判定字段。
- 检查 `summary.md` 和 `raw.json` 中的尾延迟和判定证据。

## performance/PF-8 RDMA 网络环境下仿真引擎运行能力

### 验证目标
性能要求：节点数为 4 个，10 万仿真实体，事件数量 100 万，仿真运行速度不低于 1 倍实时仿真推进速度。

- 验证大规模仿真运行的 speedup 不低于 1.0。
- 验证实体数、事件数、实体大小和节点口径可复查。
- 验证事件吞吐、仿真时间、墙钟时间和采集丢弃数可复查。

### 实现方案
- 性能脚本通过 UDS 调用 C++ 数据面 `RPC_SIM_RUN` 执行仿真负载。
- 数据面按实体数、实体大小、事件数和节点口径推进仿真。
- `raw.json` 保存 `speedup`、`events_per_sec`、`sim_s`、`wall_s`、captured/dropped 等字段。
- 当前硬件为双节点，节点口径通过结果字段明确展示。

### 测试方案

前置条件：
- C++ 数据面在线，UDS 可访问。
- 仿真引擎和采集模块已初始化。
- 测试环境内存和 CPU 资源可承载目标实体与事件规模。

测试方案：
- 调用仿真运行 RPC，提交目标实体数和事件数负载。
- 统计仿真推进时间、墙钟时间和事件吞吐。
- 计算 `speedup = simulated_seconds / wall_seconds`。
- 检查 speedup 不低于 1.0，且 captured dropped 等异常字段符合验收要求。
- 检查 `summary.md` 和 `raw.json` 中的规模参数、speedup 和判定字段。

## performance/PF-9 仿真引擎内存池化能力

### 验证目标
性能要求：使用内存池化技术后，在性能损失不超过 5% 的前提下，内存利用节省 7%；在单节点多线程高并发环境下，对 1KB 对象内存分配/释放，对比使用前吞吐量提升不低于 20%。

- 验证内存池化性能损失不超过 5%。
- 验证内存节省不低于 7%。
- 验证多线程分配/释放吞吐提升不低于 20%。

### 实现方案
- 性能脚本调用 C++ `nr_mempool_bench`，对比 malloc 基线和 slab 内存池路径。
- Slab 路径使用与生产数据面一致的固定 slot、线程本地缓存和全局 free list 模型。
- 内存节省通过独立子进程在对象存活时读取 RSS，避免不同场景互相污染。
- 结果材料保存 overhead、savings、scale gain、线程数、RSS 和吞吐对比字段。

### 测试方案

前置条件：
- `nr_mempool_bench` 可执行文件已构建。
- 单节点具备足够内存运行 1KB 对象分配/释放压测。
- 测试期间无其他高强度内存压力干扰。

测试方案：
- 执行 malloc 基线和 slab 内存池吞吐对比，计算性能损失。
- 在对象存活时采集两种路径 RSS，计算内存节省。
- 执行多线程分配/释放压测，计算吞吐提升比例。
- 检查 overhead、savings、scale gain 三个子项均满足阈值。
- 检查 `summary.md` 和 `raw.json` 中的 RSS、吞吐、阈值和判定字段。
