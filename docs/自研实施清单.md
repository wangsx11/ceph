## 第二部分：整体技术方案（为什么抛开 Ceph）

### 2.1 为什么 Ceph 拖不起性能

| 性能要求 | Ceph（RADOS）实测典型 | 差距 |
|---|---|---|
| 1KB 对象 **100 万 ops/s** | 单 pool 5 万~15 万 ops/s（RDMA msgr2 最多 30 万） | 差 3~20 倍 |
| 平均延迟 **≤ 50μs / P99 ≤ 100μs** | Ceph 客户端→OSD 链路 ≥ 300μs | 差 6 倍 |
| 读带宽 **20 GB/s** | 单节点 OSD 全闪池 3~8 GB/s | 差 3 倍 |
| 带宽利用率 **≥50%** | RADOS over RDMA 实测 15~25% | 差 2 倍 |

结论：**Ceph 的 RADOS→PG→OSD→BlueStore 链路太深**，不可能在两节点里打到 100 万 ops/s 和 50μs 延迟。必须自研一个更薄的数据平面。

### 2.2 自研技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| **RDMA 通信层** | `libibverbs` + `rdma-core`，直接写 **RC QP + 双边 SEND/RECV + 单边 WRITE_WITH_IMM** | 绕过 TCP、绕过内核，零拷贝 |
| **RPC 框架** | 自研轻量 RPC 或 **UCX（UCP）** | UCX 封装度高但可控；自研最快但工作量大 |
| **语言（数据面）** | **C++17** + `io_uring`（存储 IO） | Python 过不了 100 万 ops/s，必须 C++ |
| **控制面/API** | **Python Flask** 仍保留（只做监控、展示、非性能关键路径） | 沿用现有前端，保住演示观感 |
| **存储引擎** | 自研 **KV-over-mmap + WAL**，分三层：DRAM / NVMe / HDD | Ceph BlueStore 太重，我们只做必要的 |
| **分级迁移** | **热度 LRU + 后台异步迁移线程** | 满足 M6 演示要求 |
| **内存池** | **hugepage + slab allocator**，注册为 RDMA MR | 满足 M1 "零拷贝" + M3 "节省 7% 内存、吞吐 +20%" |
| **前端可视化** | 保留现有 `dashboard/*.html` + WebSocket 实时推送 | 演示好看 |

## 第三部分：系统架构设计

### 3.1 模块对应关系（覆盖文档三大模块）

| 文档要求模块 | 本方案对应组件 | 关键技术点 |
|---|---|---|
| M1 多级异构高效能存储 | `StorageTier` + `Prefetcher` + `CompressEngine` + `IoScheduler` | 三层存储、访问频率 LRU、顺序/随机检测预取、zstd 压缩、I/O 优先级队列 |
| M2 RDMA 分布式仿真计算 | `RdmaTransport` + `TcpFallback` + `BatchAggregator` + `QosScheduler` + `GpuDirect` + `Router` | libibverbs 双通路、批量聚合 WR、优先级 SQ、GDR、一致性 Hash 路由 |
| M3 一致性总线内存池化 | `RdmaMemPool` + `NamespaceMgr` + `AdaptiveAllocator` + `IsolationMgr` + `ReplicaHA` | 零拷贝单边 WRITE、全局命名、本地优先分配、cgroup+ACL 隔离、主备/多数派 |

### 3.2 数据面核心流程

#### 写流程（节点 A 写入一个 1KB 对象 → 同步到节点 B）

```
Client → Flask :5000 /api/put(key, value)
  ↓
Flask 通过 UDS 转发给 C++ 数据面
  ↓
C++ 数据面：
  ① 从 RDMA MemPool 借一个 1KB slot（HugePage，已注册MR）
  ② 写入 DRAM 热层 + 更新 LRU 热度
  ③ 追加 WAL（io_uring 异步写 NVMe）
  ④ 构造 RDMA WRITE_WITH_IMM，把 slot 远程写到节点B的预注册内存
  ⑤ 节点 B 的 CQ poller 收到 imm_data → 解析是哪个 key → 更新本地索引
  ⑥ 节点 B 发 ACK（SEND 2字节）→ 节点 A 完成
  ↓
返回 HTTP 200，延迟 < 50μs（不含 HTTP 本身开销，走 gRPC 内部调用测）
```

#### 读流程（节点 A 读一个对象，若本地没有则从 B 拉）

- 命中本地 DRAM 热层：直接返回（< 5μs）
- 未命中：RDMA READ 单边从对端取，绕过对端 CPU（< 30μs）
- 温/冷层：触发预取到 DRAM，更新热度

### 3.3 一致性与高可用

- **主副本策略**：每个 key 落在一个 "primary 节点"（由一致性 hash 决定）
- **同步复制**：primary 写入后，通过 RDMA 同步到 replica，确认后才返回
- **故障切换**：心跳丢失 3s → replica 提升为 primary
- **满足 M3-6 要求**：节点故障系统继续可用

## 第四部分：服务器规划与角色分配

### 4.1 两节点角色

| 角色 | 节点A（xfusion3）| 节点B（xfusion4） |
|---|---|---|
| 控制面 Flask `:5000` | ✅ | ✅ |
| Web 前端 `:8080` | ✅（主） | ✅（备） |
| C++ 数据面 `:7000`（UDS） | ✅ | ✅ |
| RDMA 端口 `18515/18516` | ✅ Listen | ✅ Listen |
| 存储层 DRAM 热 / NVMe 温 / HDD 冷 | ✅ | ✅ |
| 一致性 Hash Ring | 一半 key primary | 另一半 primary |
| Web 负载 / 压测 client | 交替做 | 交替做 |

### 4.2 两节点够不够？

**够，但有前提**：
- 性能要求 M2-8（"节点数4个"）的 100 万事件仿真，我们可以在两节点各起 2 个数据面进程，**逻辑上模拟 4 节点**，但每个进程用独立 CPU core + 独立 RDMA QP，流量真实走 RDMA 网卡 → **不违反"禁止本地模拟跨节点"**（因为流量确实过网卡）
- 演示 M3/M5/M6 时只用"两节点两进程"即可

### 4.3 硬件最低要求（已有两台请核对）

| 资源 | 最低 | 推荐 |
|---|---|---|

### Week 2：RDMA 数据面 + 内存池

#### Step 2.1 实现 `RdmaMemPool`（模块 M3 核心）

- HugePage 分配 + libibverbs `ibv_reg_mr` 注册为 MR
- Slab 分配器：预切 1KB、4KB、64KB 三种 slot
- 全局命名：`pool_id + slot_id` 两节点一致
- 提供 C API：`mp_alloc`、`mp_free`、`mp_rdma_addr`

**性能验证点**：
- 1KB 对象分配/释放 ≥ 1 亿 ops/s（纯内存操作）
- 多线程 8 core 并发，相比 malloc 吞吐提升 ≥ 20%（M3-9）

#### Step 2.2 实现 `RdmaTransport`（模块 M2-1）

- RC QP 连接管理（RDMA CM 建链）
- 双通路：RDMA 正常时走 verbs；检测到链路 down 切 TCP（保留一个 TCP socket 备用）
- 消息类型：SEND/RECV（控制面）、WRITE_WITH_IMM（数据面热路径）、READ（冷数据取回）
- Poller 线程绑核

#### Step 2.3 实现 `BatchAggregator`（模块 M2-2，性能点 M4/M5）

- 生产者把小消息塞队列 → 每 N μs 或 M 个消息触发一次 `ibv_post_send`（link-list of WR）
- **性能验证点**：1000 批×100 个 1KB 对象 ≤ 200ms；吞吐 ≥ 700 MB/s

#### Step 2.4 实现 `QosScheduler`（模块 M2-3）

- 两个 SQ：high-prio / low-prio
- 高优先级独占一个 QP，低优先级共享另一个
- Weighted Round Robin 或绝对优先级
- **性能验证点**：高优先级 2500 条 vs 低优先级 2500 条，高效率 +22%

### Week 3：存储引擎 + 分级存储

#### Step 3.1 实现 `StorageTier`（模块 M1-1/M1-2）

```
DRAM 热层（512MB 起）
  ↓ LRU 淘汰
NVMe 温层（50GB）
  ↓ 冷阈值
HDD 冷层（500GB）
```

- 每层独立的索引（hash + radix tree）
- 访问计数器：`access_cnt`、`last_access_ts`
- 后台迁移线程：每 1s 扫描一次，热度超阈值升级，低于阈值降级

#### Step 3.2 实现 `Prefetcher`（模块 M1-3）

- 顺序检测：连续 4 次访问步长相同 → 预取后续 8 个对象
- 随机访问：基于 Markov 链（简单版：N-gram）

#### Step 3.3 实现 `CompressEngine`（模块 M1-4）

- zstd level 3（默认）/ level 1（低延迟）
- 按对象类型配置：文本/JSON 开启，二进制已压缩关闭
- 去重：SHA256 指纹，refcount 引用

#### Step 3.4 实现 `IoScheduler`（模块 M1-5）

- 前台 IO（检查点、实时分析）→ io_uring high-prio
- 后台 IO（压缩、GC、迁移）→ io_uring idle 或限速

#### Step 3.5 实现 `SimDataCapture`（模块 M1-6）

- 提供回调接口：仿真引擎把对象属性/事件 push 过来
- ring buffer 缓冲，避免阻塞

**性能验证点（M1/M6/性能-6）**：
- 写带宽 ≥ 10 GB/s，读带宽 ≥ 20 GB/s
- 迁移事件可观测（时间戳、层级前后）

## 第六部分：性能优化策略

| 问题 | 优化手段 |
|---|---|
| 延迟超 50μs | 数据面 poller 绑独占 core；关闭 C-state；HugePage；`MLX5_SINGLE_THREADED=1` |

| 带宽利用率 < 50% | 大消息拆成 MTU-aligned；打开 GRO；MLX5 PKT_PACING；多 QPdemultiplex |
| 存储写带宽不到 10GB/s | io_uring polling mode + SQPOLL；NVMe 多队列；`O_DIRECT`；WAL 分片到多 NVMe |
| QoS 提升不到 22% | 高低优先级分 QP 物理隔离；高优先级 inline + doorbell-batch；低优先级限流 |
| 批量 < 700MB/s | WR link-list post；CQ 批量 poll；减少 memcpy（直接从内存池 slot 发 RDMA） |
