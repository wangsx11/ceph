## 3c - 数据同步延迟与跨节点传输行为可观测指标

### 当前实现

`backend/m3_sync.py` 的 `write_object()`（第52-63行）和 `modify_object()`（第83-97行）各自在操作前后打时间戳，测量的是"从调用 `ioctx.write_full()` 到 xattr 写完"的单节点操作耗时，返回字段 `latency_ms`。

`dashboard/m3_sync.js` 的 `syncOp()`（第490-564行）将 `latency_ms`、`hash`、操作类型写入 `syncLogs` 数组，在日志面板中显示，标注为"延迟"。

后端不存在任何跨节点可见性延迟测量逻辑，也不存在 InfiniBand 计数器读取代码（该代码仅在 `m5_perf.py` 中）。

### 与要求的差距

1. 当前展示的"延迟"是节点本地写入耗时，不是"节点A写入完成→节点B首次读到该版本"的端到端可见性延迟，两者语义不同。
2. 缺少 RDMA 网络层吞吐指标（字节收发速率）。若部署环境无 InfiniBand 设备，该项目标不可采集，需明确标记 N/A，不得使用模拟值。

### 修改方案

**步骤1：在 `backend/m3_sync.py` 中新增 `measure_visibility_latency()` 方法**

- 文件：`backend/m3_sync.py`
- 位置：`SyncModule` 类中，`read_object()` 方法之后新增
- 逻辑：
  1. 接收参数 `obj_name` 和 `expected_version`（写入操作返回的 `version` 整数值）。
  2. 记录 `t0 = time.time()`（此时刻为对端探测接口开始执行的时间，晚于写入确认时刻，包含触发探测请求的网络传输和调度开销，不是纯存储层时延）。
  3. 在循环中以最多 50ms 间隔（`time.sleep(0.05)`）反复调用 `ioctx.get_xattr(obj_name, "version")`，读取对端存储中该对象的当前版本号。
  4. 当读取到的版本号等于 `expected_version` 时，记录 `t1 = time.time()`，计算 `probe_latency_ms = round((t1 - t0) * 1000, 1)`，结束循环。
  5. 若 500ms 内未读到目标版本，返回 `probe_latency_ms = None`，表示超时未可见。
  6. 返回字典：`{"probe_latency_ms": float|None, "version": int, "obj_name": str, "timestamp": ts()}`。
- 效果：该方法由**对端节点的后端**调用，测量的是"探测请求到达对端"到"对端首次读到目标版本"之间的等待时间，即**写后对端可见性探测延迟**（含探测请求本身的网络和调度开销）。

**步骤2：在 `backend/m3_sync.py` 新增 `/api/m3/visibility_latency` 路由**

- 文件：`backend/m3_sync.py`
- 位置：`m3_read` 路由之后
- 逻辑：接收 GET 参数 `name` 和 `expected_version`（整数），调用 `sync_module.measure_visibility_latency(name, expected_version)`，返回 JSON 包含 `probe_latency_ms`、`version`、`timestamp`。

**步骤3：在 `backend/m3_sync.py` 新增 `get_rdma_throughput()` 模块级函数**

- 文件：`backend/m3_sync.py`
- 位置：`SyncModule` 类定义之前（模块级）
- 逻辑：
  1. 在函数外维护模块级字典 `_m3_rdma_last = {"ts": 0.0, "rcv": 0, "xmit": 0}`，记录上次采样的时间戳和计数器值。
  2. 函数执行时，检查 `/sys/class/infiniband` 目录是否存在。若不存在，返回 `None`。
  3. 若存在，读取第一个设备的 `ports/1/counters/port_rcv_data`（累计接收字节，4字节单位）和 `ports/1/counters/port_xmit_data`（累计发送字节，4字节单位），乘以4转为字节数。
  4. 若 `_m3_rdma_last["ts"] == 0.0`（首次调用），只将当前计数器值和时间戳写入 `_m3_rdma_last`，返回 `None`（首次无差值可算，不返回 0 值误导前端）。
  5. 后续调用：计算差值 `delta_rcv = curr_rcv - _m3_rdma_last["rcv"]`，`delta_xmit = curr_xmit - _m3_rdma_last["xmit"]`，`delta_t = time.time() - _m3_rdma_last["ts"]`。若 `delta_t < 0.1`，返回 `None`（采样间隔过短）。
  6. 更新 `_m3_rdma_last`，返回字典 `{"rcv_mbps": round(delta_rcv / delta_t / 1048576, 2), "xmit_mbps": round(delta_xmit / delta_t / 1048576, 2)}`，单位为 MB/s（二进制，1 MiB = 1048576 字节）。

**步骤4：在 `backend/m3_sync.py` 新增 `/api/m3/rdma_stats` 路由**

- 文件：`backend/m3_sync.py`
- 位置：`/api/m3/visibility_latency` 路由之后
- 逻辑：调用 `get_rdma_throughput()`。若返回非 `None`，响应 `{"available": True, "rcv_mbps": float, "xmit_mbps": float}`；若返回 `None`，响应 `{"available": False}`，**不返回任何估算值或模拟值**。

**步骤5：在 `dashboard/m3_sync.js` 的 `syncOp()` 中追加可见性探测延迟测量**

- 文件：`dashboard/m3_sync.js`
- 函数：`syncOp()`（第490行）
- 逻辑：在 `op === 'write'` 或 `op === 'modify'` 写入成功、获得 `result.version` 之后，立即对**对端节点**（写入发生在节点A则调用节点B的接口，反之亦然）发起 fetch 请求：`GET <对端API>/api/m3/visibility_latency?name=<name>&expected_version=<result.version>`。将返回的 `probe_latency_ms` 追加到该条日志末尾；若值为 `null` 则显示"可见性超时(>500ms)"，若有值则显示"对端探测延迟: Xms（含网络开销）"。

**步骤6：在 `dashboard/m3_sync.js` 中新增 RDMA 吞吐指标显示**

- 文件：`dashboard/m3_sync.js`
- 函数：`renderM3()` 的 HTML 模板字符串（第30行起）
- 逻辑：在同步日志面板上方新增两个 `metric()` 组件，分别显示"RDMA接收 X MB/s"和"RDMA发送 X MB/s"。新增 `refreshRdmaStats()` 函数，在 `startSyncPolling()` 的2秒轮询内同步调用节点A的 `/api/m3/rdma_stats`。若 `available: false`，将该区域整体替换为静态文字"RDMA指标：不可采集（无InfiniBand设备）"；若 `available: true`，更新两个数值。

### 验证方法

1. 在节点A执行 WRITE 后，日志行末尾出现"对端探测延迟: Xms（含网络开销）"，X 为正数且小于500，证明对端可见性探测路径完整。
2. 对同一对象连续写入并观察多次探测延迟数值，验证共享 Pool 下数值稳定。注意该数值包含探测请求的网络传输和调度开销，不是纯存储层时延，实际可见等待时间低于该值。
3. 在无 InfiniBand 设备的节点上，RDMA 区域显示"不可采集"而非任何数值，证明无模拟值。

## 5b - RDMA 实时吞吐量、延迟分布与网络使用率指标

### 当前实现

`backend/m5_perf.py` 的 `_run_benchmark()` 内有嵌套函数 `get_rdma_stats()`（第116-142行）。其执行逻辑：第120-126行先执行 `ceph osd perf` 命令，若该命令返回码为0（即 Ceph 集群正常可用），则**直接 `return None`**，不执行后续的 InfiniBand 计数器读取（第129-139行）。结果：在 Ceph 集群正常运行的生产环境中，第129行的 InfiniBand 读取逻辑永远不会执行，`get_rdma_stats()` 必然返回 `None`，程序进入第200行的模拟值分支：`rdma_tp = tp * (0.8 + random.uniform(0, 0.2))`。

当远端节点启动失败时，第331行将节点A的数据列表直接赋值给 `self._results_b[round_num]`，使节点B显示与节点A相同的数据，UI 无任何提示。

`backend/m5_perf.py` 第232-252行的 `summary` 字典不含网络使用率字段；`dashboard/m5_perf.js` 的 `renderPerfTable()`（第165行）和 `renderPerfChart()`（第79行）均无网络使用率展示。

### 与要求的差距

1. `get_rdma_stats()` 逻辑错误：Ceph 可用时必然返回 `None`，RDMA 曲线数据在生产环境中全部为模拟值。
2. 远端失败时节点A数据被复制为节点B数据，UI 不标注，呈现伪双节点状态。
3. 缺少网络使用率指标（当前带宽占总带宽百分比）。

### 修改方案

**步骤1：重写 `get_rdma_stats()` 函数，移除错误的 ceph 命令前置逻辑**

- 文件：`backend/m5_perf.py`
- 函数：`get_rdma_stats()`（第116-142行）
- 修改内容：
  1. 删除第119-127行的整个 `try` 块（`ceph osd perf` 调用）。该调用与 RDMA 统计无关，且其成功会导致提前返回 `None`。
  2. 在 `_run_benchmark()` 方法体外（`PerfModule` 类外）新增模块级字典 `_rdma_last = {"ts": 0.0, "rcv": 0, "xmit": 0}` 用于差值计算。
  3. 函数改为：检查 `/sys/class/infiniband` 是否存在，若不存在直接返回 `None`；若存在，读取第一个设备的 `port_rcv_data` 和 `port_xmit_data`（均为4字节单位的累计计数，乘以4转字节），计算与 `_rdma_last` 的差值除以时间间隔，返回字典 `{"rcv_mbps": float, "xmit_mbps": float}` 表示实时吞吐率（MB/s），更新 `_rdma_last`。

**步骤2：修改 `_run_benchmark()` 中的 RDMA 采样逻辑，去除模拟值，并在数据点中计算网络使用率**

## 6c - 冷数据下沉后自动触发备份与数据回迁

### 当前实现

`backend/m6_tiering.py` 的 `_demote_warm_to_cold()`（第236-252行）：将对象数据从 warm_pool 复制到 cold_pool，记录迁移事件，返回 `True/False`。方法内部不调用任何快照逻辑。

快照由 `start_demo()` 演示流程（第399-400行）在步骤4中显式调用：`self._create_snapshot(demoted)`，其中 `demoted` 是步骤3循环收集的已降级对象名列表。快照触发依赖外部流程编排，与 `_demote_warm_to_cold()` 无耦合。

`_create_snapshot()`（第254-291行）：读取 cold pool 中各对象数据，仅将 `size` 和 `hash` 字段写入本地 JSON 文件（路径 `~/ceph-web/data/snapshot_*.json`，第274行），不保存对象实际数据内容，不写入 Ceph 集群。

快照详情接口 `/api/m6/snapshot/<name>`（`backend/m6_tiering.py` 第545行对应的路由）依赖读取本地 JSON 文件内容返回前端。

### 与要求的差距

1. 快照触发在 `start_demo()` 步骤4显式调用，`_demote_warm_to_cold()` 不调用快照逻辑，不满足"自动触发"语义。
2. 快照仅保存 size + hash 元数据，未保存对象实际数据，不满足"备份"的完整含义。
3. 快照文件存储在本地文件系统，与 Ceph 集群无关联。

### 修改方案

**步骤1：在 `config.py` 中新增备份专用 Pool 配置项**

- 文件：`backend/config.py`
- 位置：`COLD_POOL` 配置行之后
- 修改内容：新增 `BACKUP_POOL = os.environ.get("BACKUP_POOL", "backup_pool")`。备份对象写入此独立 Pool，与 cold_pool 的冷层对象完全隔离，不影响冷层对象计数和迁移语义。

**步骤2：修改 `_demote_warm_to_cold()`，在方法内部自动登记备份任务**

- 文件：`backend/m6_tiering.py`
- 函数：`_demote_warm_to_cold()`（第236-252行）
- 修改内容：在 `self._migration_history[obj_id] = time.time()`（第242行）之后，新增 `self._pending_snapshot_objs.append(obj_id)`，将本次成功降级的对象名追加到实例变量 `_pending_snapshot_objs`（在 `__init__` 中初始化为 `[]`）。同时在 `reset()`（第488行）中新增 `self._pending_snapshot_objs = []`，防止 reset 后重跑 demo 时上次遗留的 pending 对象混入本次备份。此操作在降级流程内自动完成登记，不立即执行备份 IO，避免每次降级都触发 IO 操作导致事件爆炸。备份 IO 由后续阶段统一批量落盘（见步骤4）。

**步骤3：新增 `_flush_snapshot_to_ceph()` 方法，对本轮 pending 对象执行批量备份**

- 文件：`backend/m6_tiering.py`
- 前置：在第14行 `from config import (...)` 的括号内补充 `BACKUP_POOL`，否则后续步骤运行报 `NameError`。
- 位置：`_create_snapshot()` 方法之后新增
- 逻辑：
  1. 若 `self._pending_snapshot_objs` 为空，直接返回。
  2. 获取当前 `_pending_snapshot_objs` 的副本，清空 `self._pending_snapshot_objs`。
  3. 打开 cold pool（`_get_cold_ioctx()`）和 backup pool（新增 `_get_backup_ioctx()` 方法，逻辑与 `_get_cold_ioctx()` 相同，使用 `BACKUP_POOL` 常量）。
  4. 遍历待备份对象列表：读取每个对象的完整数据（`ioctx_cold.read(obj_id)`），将数据写入 backup pool，对象名保持不变（`ioctx_backup.write_full(obj_id, data)`），并通过 `set_xattr` 记录元数据：`backup_time`（时间戳）、`source_pool`（`cold_pool` 的实际值）、`data_hash`（`compute_hash(data)` 结果）。
  5. 计算总耗时，构造快照事件追加到 `self._snapshot_events`，字段：`ts`、`name`（格式 `backup_<timestamp>`）、`count`（备份对象数量）、`dur`（格式 `X.XXs`）、`storage`（`"ceph_backup_pool"`）。
  6. 写入本地 JSON 元数据文件（供 `/api/m6/snapshot/<name>` 路由读取）：复用 `_create_snapshot()` 的 JSON 写入逻辑，文件名格式同为 `snapshot_<timestamp>.json`，写入字段为 `name`、`timestamp`、`objects`（每个对象的 `size` 和 `hash`）、`count`、`"storage": "ceph_backup_pool"`、`"backup_count": int`。`_create_snapshot()` 原方法保持不变，但不再从 demo 流程调用；`_flush_snapshot_to_ceph()` 承担全部写入职责（Ceph 数据 + 本地 JSON），保证快照详情接口不受影响。

**步骤4：修改 `start_demo()` 步骤4，将显式快照调用改为调用批量备份方法**

- 文件：`backend/m6_tiering.py`
- 函数：`start_demo()`，第399-400行
- 修改内容：将 `self._create_snapshot(demoted)` 改为 `self._flush_snapshot_to_ceph()`（无需传参，从 `_pending_snapshot_objs` 取数据）。步骤4的职责变为：触发将步骤3中已自动登记的待备份对象批量写入 backup_pool，并生成汇总事件和 JSON 元数据文件。设计语义为：**降级流程内自动登记备份任务，下一阶段自动批量落盘**，而非由外部流程传入对象列表显式触发。步骤3中每次 `_demote_warm_to_cold()` 成功时仅追加到 pending 列表，步骤4统一执行备份 IO，节奏与演示流程一致。

**步骤5：在 `dashboard/m6_tiering.js` 的快照详情展示中，标注备份存储位置**

- 文件：`dashboard/m6_tiering.js`
- 函数：`toggleSnapDetail()`（第348行）
- 逻辑：在快照详情展开区域的标题行新增存储位置标注。从快照事件数据的 `storage` 字段取值：若为 `"ceph_backup_pool"` 则显示绿色标注 `[已备份至 Ceph backup_pool]`；若字段不存在（兼容旧格式）则不显示额外标注。

### 验证方法

1. 运行演示流程到步骤3时，在 `_pending_snapshot_objs` 中确认对象已积累，快照事件列表无新增（证明步骤3不触发 IO）；步骤4完成后，快照事件列表出现一条新记录，证明批量触发机制有效。
2. 步骤4完成后执行 `rados -p backup_pool ls`，确认输出中出现与降级对象同名的对象，证明实际数据已写入 Ceph backup_pool，而非仅存在于本地文件系统。
3. 对任意已备份对象执行 `rados -p backup_pool get <obj_id> /tmp/verify.dat`，计算其 SHA256 与 xattr 中 `data_hash` 对比，两者一致，证明备份保存了完整数据。
4. 快照详情 UI 展开时，显示"已备份至 Ceph backup_pool"标注，并列出备份对象名和 hash 值。

## 修改优先级排序

按"演示评审中被质疑的风险"从高到低：

| 优先级 | 条目 | 风险描述 |
|--------|------|----------|
| 1 | **5b — 修复 `get_rdma_stats()` 逻辑缺陷** | 在 Ceph 集群正常运行的生产环境中，RDMA 数据**必然**全部为模拟值。若评审现场要求查看代码或对比 `ibstat` / 系统计数器数据，立即暴露。这是确定性 bug，不依赖部署环境，必须修复。 |
| 2 | **5b — 禁止单节点回退时复制节点A数据** | 远端失败时 UI 显示双节点数据但实为同一份数据，若评审询问"两节点数值为何完全相同"或"节点B的数据从哪来"，无法自圆其说。 |
| 3 | **6c — 将快照实际数据写入独立 Ceph Pool** | 当前快照为本地 JSON 元数据文件，若评审要求验证"备份在哪"并执行 `rados ls`，无法在 Ceph 中找到对应对象，质疑备份有效性。 |
| 4 | **6c — 将快照触发逻辑内置到降级流程** | 代码层面 `_demote_warm_to_cold()` 不调用任何快照逻辑，与"自动触发"表述不符。若评审翻阅代码，会发现快照是步骤4显式调用的，而非降级操作自动触发。 |
| 5 | **3c — 增加跨节点可见性延迟测量** | 当前"延迟"仅为本地写入耗时，若评审追问"同步延迟是怎么测的"，现有日志无法回答"A写入后B多久可见"。 |
| 6 | **5b — 新增网络使用率指标** | 要求明确列出"网络使用率"，当前仅有绝对吞吐值，缺少百分比换算。影响相对较小，但对照要求属于明确缺失项。 |
| 7 | **3c — RDMA 吞吐指标展示** | 依赖 InfiniBand 硬件可用性。若有硬件则可补充；若无，明确标注 N/A 即可通过，对评审影响最小。 |
