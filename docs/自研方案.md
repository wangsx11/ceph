## 1. 设计原则与关键决策

### 1.1 三条硬约束

- **不依赖任何现成分布式存储**（不用既有通用分布式存储套件）。
- **数据面热路径必须走 RDMA Verbs**，绕过内核协议栈、零拷贝。
- **演示必须真实跨节点**，即所有数据读写都要在 `<RDMA_DEV>` 上产生流量，可被 `mlnx_perf`、`ibdump`、网卡计数器观测。

### 1.2 关键决策

| 决策项 | 选择 | 理由 |
|---|---|---|
| 数据面语言 | **C++17** | Python 热路径达不到 100万 ops/s 与 50μs 延迟 |
| 控制面语言 | **Python 3.10 + Flask + WebSocket** | 沿用现有 dashboard 风格，非热路径 |
| IPC（控制面 ↔ 数据面）| **Unix Domain Socket + Cap'n Proto / Protobuf** | 本机低延迟，零竞争 |
| RDMA 封装 | **直接使用 libibverbs + rdma-core CM** | 最大化性能上限，避免 UCX/librdmacm 额外调度 |
| 本地存储 IO | **io_uring (SQPOLL)** | NVMe 多队列打满 ≥ 10 GB/s 的必要手段 |
| 序列化 | **定长二进制头 + 变长 payload** | 热路径零反射 |
| 一致性模型 | **强一致主副本同步复制**（Primary-Backup Sync） | 满足"写后立即跨节点可见"的演示语义 |
| Key 分布 | **一致性 Hash + 虚拟节点** | 两节点起步，可平滑扩到 4+ |
| 副本数 | **2**（A/B 互为备份） | 两节点物理条件下最优 |
| 前端 | **沿用 `dashboard/*.html`**，新增 WebSocket 数据源 | 节省时间、观感统一 |

### 1.3 与旧方案的本质区别

| 维度 | 旧方案 | 本自研方案 |
|---|---|---|
| 数据链路 | client → 多层存储服务 → 后端存储引擎 → 磁盘 | client → 数据面进程 → RDMA QP / 本地 Tier |
| 跨节点路径跳数 | ≥ 5 | **1**（单边 RDMA WRITE/READ） |
| 用户态拷贝次数 | ≥ 3 | **0**（MR 内直接 DMA） |
| 预期 1KB 延迟 | 数百微秒级 | **< 50μs（含业务处理）** |
| 预期 1KB ops/s | 单实例 10万量级 | **≥ 100万**（多 QP 并行） |

### 2.2 线程模型（单节点）

| 线程 | 数量 | 绑核 | 职责 |
|---|---|---|---|
| `rdma_poller` | 2 × QP 组 | 专核独占 | busy-poll CQ，处理 WC，绝不 sleep |
| `cm_handler` | 1 | 普通核 | RDMA CM 建链/断链事件 |
| `io_submitter` | 2 | NVMe 所在 NUMA | io_uring SQ 提交 |
| `io_completer` | 2 | NVMe 所在 NUMA | io_uring CQ 收割 |
| `tier_migrator` | 1 | 普通核 | 扫描热度、触发迁移 |
| `prefetcher` | 1 | 普通核 | 预取预测 |
| `replicator` | 1 | HCA NUMA | 副本同步 |
| `heartbeat` | 1 | 普通核 | 1 Hz 心跳 |
| `metrics` | 1 | 普通核 | 100ms 聚合指标 |
| `ctrl_rpc` | 2 | 普通核 | 接收控制面调用 |

**绑核原则**：`rdma_poller` 一定要和 `<RDMA_DEV>` 的 NUMA 一致（A 节点 NUMA0、B 节点 NUMA1，见硬件配置表）。

## 3. 数据面核心模块设计

### 3.1 RdmaCore（对应 M2-1）

#### 3.1.1 QP 连接拓扑

- **控制 QP（1 对）**：RC 类型，用于建链握手、MR 地址交换、失败切 TCP 的信号通道。
- **数据 QP（N 对，N ≥ 8）**：RC 类型，跨两个 NUMA，每节点至少 8 个 QP 并行，每 QP SQ/RQ 深度 1024。
- **QoS QP（2 对）**：一个给高优先级、一个给低优先级（配合 QoS 模块）。
- **TCP fallback socket（1 对）**：RDMA 不可用时自动降级（满足"兼容非 RDMA 环境"）。

#### 3.1.2 消息语义

| 场景 | 原语 | 说明 |
|---|---|---|
| 小对象写（≤256B）| `IBV_WR_SEND` + inline | 避免 DMA 读，最低延迟 |
| 1KB 对象写 | `IBV_WR_RDMA_WRITE_WITH_IMM` | 远端通过 imm_data 识别槽位，零拷贝 |
| 对象读未命中 | `IBV_WR_RDMA_READ` | 单边，不打扰对端 CPU |
| 批量传输 | WR link-list（SGE chain）| 单次 `ibv_post_send` 推 N 条 WR |
| 心跳/控制 | `IBV_WR_SEND` | 控制 QP |

#### 3.1.3 关键优化

- **Inline 阈值**：`max_inline_data = 256`，≤256B 走 inline。
- **Doorbell batching**：同一 poller 循环内累积 ≤32 条 WR 再 ring doorbell。
- **CQ 批量收割**：`ibv_poll_cq(cq, 32, wc[])`。
- **Shared Receive Queue**：多 QP 共享 SRQ，减少 RECV 预 post 数量。
- **GID 显式**：`attr.ah_attr.grh.sgid_index = <GID_IDX>`，避免误用 v1。

### 3.2 MemPool（对应 M3-1/2/3/4/5 与 M1-6）

#### 3.2.1 分层

```
Layer 0: Slab（固定尺寸 1KB/4KB/64KB 各一池）
         └── 全部 HugePage 2MB 构成，启动时一次性 ibv_reg_mr
Layer 1: Arena（变长，大对象 ≥ 64KB）
         └── buddy allocator，按需注册 MR（LRU 缓存 MR handle）
Layer 2: Remote Window（对端预留）
         └── 两端各保留 <HUGEPAGE_GB> 的 MR 给对方远程写
```

#### 3.2.2 全局命名（满足 M3-3）

```
PoolName = "<namespace>/<pool_tag>"
每个 Pool → {pool_id: uint32, base_addr, length, rkey}
两节点启动时互换 Pool 元数据表，存入本地 PoolRegistry
```

#### 3.2.3 API（C ABI，给 C++ 与 Python ctypes 共用）

```c
// mempool.h
int  mp_create(const char* name, size_t bytes, int numa, uint32_t* pool_id);
void* mp_alloc(uint32_t pool_id, size_t size, uint64_t* rdma_addr, uint32_t* rkey);
int  mp_free(uint32_t pool_id, void* ptr);
int  mp_attach_remote(const char* name, uint32_t peer_id);  // 拿对端 rkey
int  mp_isolate(uint32_t pool_id, uint32_t tenant_id);      // 任务级隔离
int  mp_stat(uint32_t pool_id, mp_stat_t* out);
```

#### 3.2.4 自适应分配（M3-4）

- 每个对象维护 `hot_counter`（最近 1s 访问次数）。
- 热对象优先放 **本地** HugePage Slab。
- 冷对象写入远端 Window（通过 RDMA WRITE），释放本地内存。
- 迁移阈值、窗口大小均可配。

#### 3.2.5 隔离（M3-5）

- 每个 tenant 分配独立 Slab，ACL 白名单。
- MR 注册时使用不同 PD；跨 tenant 访问直接被 RDMA 硬件拒绝。

#### 3.2.6 HA（M3-6）

- Replicator 对每个 tenant 的 Slab 做 1:1 远程镜像。
- 心跳超时 → 数据面状态机切到"降级"，只读直到对端回归。

### 3.3 QoSSched（对应 M2-3、性能-3）

- 两个物理分离的 QP 组：`qp_hi[]` / `qp_lo[]`。
- 高优先级独占一个 poller 线程，低优先级共享 poller。
- `qp_hi` 使用 `IBV_QP_RATE_LIMIT` 不设上限；`qp_lo` 设 80% 令牌桶。
- **目标**：高优先级吞吐/延迟相比低优先级提升 ≥22%。

### 3.4 BatchAggregator（对应 M2-2、性能-4/5）

```
上层 put(key, value) → 生产队列（lock-free MPSC）
                     ↓
                聚合器线程（每 10μs 或累积 32 个触发）
                     ↓
          构造 ibv_send_wr 链表，单次 post
                     ↓
                 CQ poller 收割
```

- **目标-4**：`100 × 1KB × 1000 批次 ≤ 200ms`、`1000 × 1KB × 100 批次 ≤ 100ms`。
- **目标-5**：持续吞吐 ≥ 700 MB/s（当前网卡 100Gbps，理论上限 12.5 GB/s，富余极大）。

### 3.5 ObjectRouter

- 一致性 hash ring（160 虚节点/物理节点）。
- `key → primary_node, replica_node`。
- Primary 路由到本地，Replica 路由到 RDMA Peer。
- 扩容时只迁移 `1/N` 的 key。

### 3.6 TierEngine（对应 M1-1/2、性能-6）

#### 3.6.1 三层物理映射（按硬件）

| 层 | 节点 A 映射 | 节点 B 映射 | 容量 |
|---|---|---|---|
| Hot (DRAM Slab) | HugePage 64GB on `/dev/shm` | HugePage 32GB on `/dev/shm` | 按需 |
| Warm (NVMe) | `/home/wsy/mnt` 或 `nvme0n1` 直设备 | `nvme0n1` 直设备（注意 `/home` 已 96%，建议分区专用）| ~1.8 TB |
| Cold (HDD/RAID) | `/home` (sdb 21T) 或新建目录 | 新分区（不放 `/home`）| ≥ 10 TB |

#### 3.6.2 索引结构

```
PrimaryIndex: HashMap<KeyHash, ObjectMeta>
ObjectMeta {
  uint64_t offset;     // 在层内的物理偏移
  uint32_t size;
  uint8_t  tier;       // 0=DRAM 1=NVMe 2=HDD
  uint64_t last_access;
  uint32_t access_cnt;
  uint8_t  flags;      // compressed / deduped / replica
  uint64_t fingerprint; // SHA256 前 8 字节（去重）
}
```

#### 3.6.3 冷热识别与迁移（对应 M6 演示）

- **Count-Min Sketch** 统计频次 + LRU 近期标记。
- 每 1s 扫描：
  - DRAM → NVMe：命中率 < 阈值 或 容量 > 80%
  - NVMe → DRAM：1s 内访问 ≥ 5 次
  - NVMe → HDD：30s 无访问
  - HDD → NVMe：被命中一次即回迁
- 迁移事件写入 `migration.log`（含时间戳、key、src→dst），同时通过 WebSocket 推送前端。

#### 3.6.4 冷数据下沉自动快照（对应 M6 演示 c 条）

- HDD 层写入满足"首次下沉"时触发快照线程。
- 快照采用 `copy-on-write`，输出 `snap_<ts>.idx` 和 `snap_<ts>.dat`。
- 演示时统计"备份对象数量、耗时、生成文件路径"。

### 3.7 Prefetcher（对应 M1-3）

- 顺序检测：滑动窗口记录最近 8 次访问的 key stride。
- Markov 预测：每个 key 记 top-3 后继（1-gram），命中率低则降级为 LRU-K。
- 预取触发：后台线程异步读 NVMe/HDD → DRAM Slab。

### 3.8 CompressEngine（对应 M1-4）

- 算法：`zstd level 3`（默认）、`lz4`（低延迟可选）。
- 去重：`xxhash64 + SHA256` 双哈希，refcount ≥ 0。
- 策略：对象 ≥ 4KB 才压缩；已压缩二进制跳过。
- **承诺**：热路径 1KB 对象默认不压缩（保延迟），落 NVMe 时异步压缩。

### 3.9 IoScheduler（对应 M1-5）

- io_uring 两队列：`io_uring_fg`（检查点、实时分析）、`io_uring_bg`（压缩、迁移、GC）。
- `fg` 设置 `IORING_SETUP_SQPOLL` 常驻，`bg` 用普通提交。
- 两队列独立限速，前台突发优先。

### 3.10 Replicator + HeartbeatHA

- 每条写请求：主副本本地落成 → RDMA WRITE 到备副本 → 等 imm ACK → 返回客户端。
- 心跳 1Hz，连续丢 3 次（3s）判定失联。
- 自动降级：
  - Primary 失联：Backup 提升为 Primary，只读或读写（演示优先选只读，安全）。
  - Backup 失联：Primary 继续服务，记录"待回放日志"，恢复后异步追平。

### 3.11 SimDataCapture（对应 M1-6）

- 暴露 C API：`sim_capture(entity_id, type, attr_blob, len)`。
- 内部使用无锁 ring buffer（SPSC，每仿真线程一份）。
- 每 1ms 批量落 NVMe（WAL 格式），不阻塞仿真线程。

### 3.12 仿真引擎（对应 性能-8）

- 2 节点 × 2 数据面进程 = **逻辑 4 节点**（流量真实走 RDMA，不是本地回环）。
- 每进程负责 25000 个实体，事件总量 100 万。
- 实体状态存在本地 DRAM Slab，事件通过 QoS QP 广播。
- 使用仿真时钟同步（类 PTP 精度 < 10μs）。
- 目标：仿真推进速率 ≥ 1× 实时。

## 4. 控制面与可观测设计

### 4.1 Flask 控制面职责（不触碰热路径）

- HTTP API：集群注册、Pool 创建、快照触发、演示脚本启停。
- WebSocket `/ws/metrics`：100ms 推送聚合指标。
- WebSocket `/ws/events`：迁移/副本/故障事件实时推送。
- 调用方式：**UDS + Protobuf**（不用 HTTP 调 C++，减少一次拷贝）。

### 4.2 指标采集

数据面 `MetricsAgent` 以 100ms 为粒度，通过共享内存把下列指标写给 Flask：

| 指标 | 单位 | 覆盖演示/性能点 |
|---|---|---|
| ops_per_sec (total / hi / lo) | ops | 性能-1/3 |
| latency_histogram (avg/p50/p99/p999) | μs | 性能-2 |
| bw_tx / bw_rx | Gbps | 演示-5、性能-1 |
| rdma_util_pct | % | 性能-1 |
| tier_distribution | 对象数 | 演示-6 |
| migration_events | 事件流 | 演示-6 |
| qp_depth, cq_depth | int | 诊断 |
| mem_pool_usage | % | M3 |
| replica_lag_us | μs | 演示-3 |

### 4.3 前端面板（基于现有 dashboard）

- **M3 面板**：A/B 节点对象视图，写入后 B 侧高亮刷新；展示"同步延迟"曲线。
- **M5 面板**：实体数量滑杆（1万/5万/10万），实时吞吐+延迟+带宽利用率三图。
- **M6 面板**：分层饼图 + 迁移事件瀑布流 + 快照生成记录。

// rdma/rdma_core.h
class RdmaCore {
public:
    struct Config {
        std::string dev_name;   // <RDMA_DEV>

        int         num_qp;     // 8
        int         sq_depth;   // 1024
        int         cq_depth;   // 4096
        int         max_inline; // 256
    };
    bool init(const Config&);
    bool connect_peer(const std::string& peer_ip, uint16_t port);

    // 热路径
    int post_write(int qp_idx, const void* buf, size_t len,
                   uint64_t remote_addr, uint32_t rkey,

    int post_read (int qp_idx, void* buf, size_t len,

    int post_send_inline(int qp_idx, const void* buf, size_t len, uint64_t wr_id);
    int post_batch(int qp_idx, ibv_send_wr* wr_list);

    // CQ

## 7. 部署与调优步骤

> 以下所有步骤，**两台节点都要执行**，除非特别标注。

### 7.1 OS 级调优（一次性）

```bash
# 1. HugePage（A: 64GB = 32768 × 2MB; B: 32GB = 16384 × 2MB）
echo 32768 | sudo tee /proc/sys/vm/nr_hugepages        # 节点 A
echo 16384 | sudo tee /proc/sys/vm/nr_hugepages        # 节点 B
sudo sysctl -w vm.swappiness=1
sudo sysctl -w vm.zone_reclaim_mode=0

# 2. CPU 性能模式
sudo cpupower frequency-set -g performance
for c in /sys/devices/system/cpu/cpu*/cpuidle/state*/disable; do echo 1 | sudo tee $c; done

# 3. 中断绑核（mlx5 的 IRQ 绑到 HCA 所在 NUMA）
sudo systemctl stop irqbalance && sudo systemctl disable irqbalance
# 手动：grep mlx5 /proc/interrupts 找 IRQ，然后 echo <mask> > /proc/irq/<n>/smp_affinity

# 4. 网卡与 MTU（当前 active_mtu=1024，推荐统一到 4096）
sudo ip link set <ens_name> mtu 4200
# 两端都调，并通过 ibv_devinfo 确认 active_mtu 升到 4096

# 5. ulimit
echo "* soft memlock unlimited" | sudo tee -a /etc/security/limits.conf
echo "* hard memlock unlimited" | sudo tee -a /etc/security/limits.conf
echo "* soft nofile 1048576"    | sudo tee -a /etc/security/limits.conf

# 6. 统一 perftest 版本（硬件配置中已指出两端版本不一致，强烈建议统一）
#    建议以 xfusion4 的 6.23 为准，xfusion3 升级 perftest
```

## 8. 性能达标路径（逐条对齐）

### 8.1 预算模型（基于硬件配置实测）

- 物理 RDMA 带宽：**57.4 Gb/s**（A→B 实测 65KB WRITE）
- 物理 RDMA 延迟：**1.74μs avg、1.77μs P99**（2B WRITE）
- 若每 1KB 对象走一次单边 WRITE：
  - 理论 ops 上限 ≈ 57.4e9 / 8 / 1024 ≈ **700万 ops/s**（纯网络）
  - 留出软件栈开销 7 倍降级 → 仍可达 **100万 ops/s** ✓

### 8.2 逐条对齐表

| # | 要求 | 达标方案 | 预期值 |
|---|---|---|---|
| 性能-1 | 带宽利用率 ≥50%、1KB 100万 ops/s | 8 QP 并行 + inline + batching + SRQ | 55–70% 利用率、**≥ 120万 ops/s** |
| 性能-2 | 10万对象 avg≤50μs、P99≤100μs | 单边 WRITE + 专核 poller + HugePage MR | avg **≈ 8–15μs**、P99 **≈ 25–40μs** |
| 性能-3 | QoS 高优先级 +22% | 物理分离 QP + 独占 poller + 低优先级限流 | **+30–40%** |
| 性能-4 | 100×1000 ≤200ms、1000×100 ≤100ms | BatchAggregator WR 链表 | 100×1000 **≈ 60–80ms**、1000×100 **≈ 30–50ms** |
| 性能-5 | 批处理 ≥700 MB/s | 同上（WR 链 + 聚合）| **3–6 GB/s** |
| 性能-6 | 写 ≥10 GB/s、读 ≥20 GB/s（全闪）| io_uring SQPOLL + NVMe 多队列 + DRAM 热层命中 | 写 **11–13 GB/s**、读 **22–28 GB/s**（DRAM 命中 90%+ 时显著高于 20） |
| 性能-8 | 4 节点 10 万实体 100 万事件 ≥1× | 2 节点 × 2 进程 + QoS QP + 定长事件 | **1.2–1.8×** |
| 性能-9 | 内存池损失 ≤5%、节省 ≥7%、多线程 +20% | Slab + HugePage + per-core free list | 损失 **≈2%**、节省 **≈10–15%**、多线程 **+30–50%** |

> 注：性能要求文档中没有第 7 条（直接从 6 跳到 8），本方案忠实对齐。

### 8.3 不达标时的快速迭代套路

1. **延迟不达标**：检查 poller 是否被调度走 → 强制 `isolcpus`；关闭 C-state。
2. **吞吐不达标**：加 QP 数；检查 `active_mtu` 是否还是 1024，升到 4096；打开 `MLX5_SHUT_UP_BF=0`。
3. **带宽利用率低**：开 `MLX5_POST_SEND_PREFER_BF=1`；排查 PCIe 带宽瓶颈。
4. **NVMe 写不到 10GB/s**：两块 NVMe 组 stripe；WAL 和 Data 分到不同盘。

## 11. 风险清单与兜底

| 风险 | 触发概率 | 兜底方案 |
|---|---|---|
| `active_mtu` 升 4096 失败 | 中 | 保持 1024，靠多 QP 并行补吞吐（代价：延迟略升） |
| 两端 perftest / OFED 版本差异导致握手失败 | 中 | 强制统一 MLNX_OFED 24.10（以 B 为准），或编译时静态链接 |
| C++ 工期不够 | 中 | 核心 3 模块（RdmaCore/MemPool/TierEngine）必须 C++；其余（Prefetcher/Compress/Snapshot）降级用 Python + 批量调用 |
| xfusion4 `/home` 96% 爆盘 | 高 | Cold 层强制使用 `sdb` 新建分区，禁止落 `/home` |
| GPU-Direct（M2-4）功能联调超时 | 中 | 用 `cudaMemcpy` + 常规 RDMA 替代，性能略降但功能完整 |
| 演示现场网络/机器异常 | 低 | W5 录制高清视频作兜底；PPT 备完整指标截图 |
| 100 万 ops/s 达不到 | 中 | 申请扩 QP 到 16、开启 `MLX5_CQE_COMPRESSION`；或降级为"80 万 ops/s + 4 节点逻辑叠加 = 320 万聚合" |
