## 第 3 项：基于 RDMA 跨节点对象读写与数据同步能力演示

### 3a. 构建不少于两个节点的运行环境，共享同一分布式共享数据空间

**结论：已满足**

代码实现情况：
- `config.py` 配置了两个物理节点：xfusion3（节点A，192.168.0.3）和 xfusion4（节点B，192.168.0.4）
- 两节点共享同一 Ceph RADOS 存储池 `sync_pool`（`config.py:8`）
- `m3_sync.py` 的 `SyncModule` 类通过 `ceph_mgr` 连接真实 Ceph 集群，调用 `rados.Rados` 原生接口
- 前端 `m3_sync.js` 通过 `API_BASE_A` 和 `API_BASE_B` 两个独立地址分别连接两个节点的 Flask 后端
- `buildNodes()` 函数执行 5 步初始化，其中第 3 步调用两个节点的 `/api/m3/cluster` 验证双节点均可达

### 3b. 在节点A写入对象，在节点B进行读取、修改及回写，所有变更在两节点可视化界面实时呈现

**结论：已满足**

代码实现情况：
- `m3_sync.py` 提供完整的 CRUD 操作：`write_object`、`read_object`、`modify_object`、`delete_object`，均接受 `node` 参数标识操作来源节点
- 每个操作通过 `set_xattr` 记录 `created_by`/`modified_by` 元数据，可追溯写入/修改节点
- 版本号通过 xattr `version` 自增跟踪修改历史
- 前端以双面板形式展示两个节点（`renderSyncNodePanel`），每个面板独立显示对象列表
- 2 秒轮询间隔（`startSyncPolling`）自动刷新两侧数据
- 因为底层是共享 Ceph Pool，节点 A 写入的对象节点 B 可立即读取，无需额外同步机制

### 3c. 系统须展示数据同步延迟、跨节点传输行为等可观测指标

**结论：部分满足**

已实现的部分：
- 每次操作记录并展示操作延迟（`latency_ms`），精确到 0.1ms（`m3_sync.py:63,97,121`）
- 同步指标日志实时展示：时间戳、操作类型（WRITE/MODIFY/DELETE）、操作延迟、数据哈希、版本号
- 哈希一致性校验（`compute_hash`），显示 "一致 ✓" 标记

**存在的差距：**
1. **缺少显式的跨节点同步延迟指标**：当前展示的是单次操作延迟（从发起到 Ceph 确认），而非 "节点A写入后节点B可见" 的端到端同步延迟。虽然共享 Pool 下两者近似等价，但缺少专门的同步延迟测量（如：A 写入后立即从 B 读取并计算时间差）
2. **缺少跨节点传输行为的详细指标**：未展示 RDMA 网络层面的传输指标，如传输带宽、数据包数量、网络往返时间等。当前仅有应用层的操作延迟
3. **缺少数据一致性延迟的量化展示**：未测量从写入到另一节点可见的时间窗口

### 3d. 本地模拟跨节点的演示视为无效演示

**结论：已满足**

代码实现情况：
- 系统依赖真实 Ceph 集群部署在两个物理节点上
- 前端连接两个不同 IP 地址的后端服务（`API_BASE_A`/`API_BASE_B`）
- `buildNodes()` 步骤 3 实际调用两个节点的 API 验证连通性，若任一节点不可达则抛出异常
- 不存在本地模拟代码，所有存储操作均通过 `rados.Rados` 连接真实 Ceph 集群

## 第 5 项：系统吞吐量及实体数量增加对性能影响演示

### 5a. 在至少两个节点下逐步增加对象数量（例如 1 万、5 万、10 万等），并对系统施加持续并发读写负载

**结论：已满足**

代码实现情况：
- 三轮递增测试：10,000 / 50,000 / 100,000 对象（`m5_perf.py:273`，`counts = {1: 10000, 2: 50000, 3: 100000}`）
- 每轮 16 线程并发（`m5_perf.py:275`），70% 读 / 30% 写比例（`m5_perf.py:144`）
- 每轮持续 12 秒（`m5_perf.py:275`）
- 双节点并行：协调节点（A）通过 HTTP 调用 `/api/m5/start_remote` 启动远程节点（B）测试（`m5_perf.py:300-310`）
- 预填充阶段使用 16 线程并行写入 4KB 对象（`m5_perf.py:86-104`）
- 实际对 Ceph RADOS `perf_pool` 执行真实读写操作

### 5b. 实时展示 RDMA 实时吞吐量、延迟分布、网络使用率等指标，并以曲线形式展示实体数量增长对系统性能的影响

**结论：部分满足**

已实现的部分：
- **实时指标采集**：每秒采集一次 IOPS、吞吐量（MB/s）、平均延迟（ms）、RDMA 吞吐量（`m5_perf.py:187-220`）
- **四条实时曲线**：IOPS、吞吐量、延迟、RDMA 网络吞吐，均以 SVG 图表实时渲染（`m5_perf.js:79-163`）
- **三轮叠加对比**：三轮数据以不同颜色叠加在同一图表上，直观展示对象数量增长的影响
- **延迟分布**：汇总表展示 P50/P90/P99 百分位延迟（`m5_perf.py:243-245`）
- **双节点汇总**：当双节点均有数据时，汇总 IOPS 并分别展示各节点贡献（`m5_perf.py:232-252`）

**存在的差距：**
1. **RDMA 吞吐量数据可能为模拟值**：代码尝试读取 `/sys/class/infiniband/*/ports/1/counters/port_rcv_data` 获取真实 RDMA 网卡统计，但当硬件计数器不可用时回退为模拟值 `tp * (0.8 + random.uniform(0, 0.2))`（`m5_perf.py:200`）。若部署环境缺少 InfiniBand 设备，RDMA 数据将全部为模拟值
2. **缺少网络使用率指标**：要求展示 "网络使用率"，但当前仅展示 RDMA 吞吐量（绝对值 MB/s），未展示为网络带宽的百分比利用率
3. **RDMA 读取逻辑存在问题**：`get_rdma_stats()` 先调用 `ceph osd perf` 命令（`m5_perf.py:120-126`），若成功则返回 `None`（导致进入模拟分支），逻辑不够清晰，可能导致即使有真实 RDMA 硬件也无法正确采集

### 5c. 本地模拟跨节点的演示视为无效演示

**结论：已满足（有条件）**

代码实现情况：
- 协调节点通过 HTTP 请求远程节点的 `/api/m5/start_remote` 启动并行测试（`m5_perf.py:300-310`）
- 两个节点各自独立对共享 `perf_pool` 执行真实 Ceph 读写
- 测试完成后协调节点轮询远程节点的 `/api/m5/live` 获取结果并汇总

**潜在风险：**
- 当远程节点启动失败时，代码回退为单节点模式（`m5_perf.py:311,331`：`self._results_b[round_num] = list(self._results[round_num])`），将节点A的数据复制为节点B的数据。此行为虽为容错设计，但若演示时实际以单节点模式运行，评审可能质疑其真实性
- 建议在 UI 上明确标注当前是双节点还是单节点模式运行

## 第 6 项：分级存储能力演示

### 6a. 演示真实访问行为完成冷热数据识别，并在三层分级存储环境（内存、SSD、HDD）下自动执行数据提升与下沉

**结论：已满足**

代码实现情况：
- **三层存储架构**：
  - 热层（DRAM）：`/mnt/hot` ramfs 文件系统（`config.py:12`）
  - 温层（SSD）：Ceph `warm_pool`（`config.py:10`）
  - 冷层（HDD）：Ceph `cold_pool`（`config.py:11`）
- **热度计算**：基于时间衰减的访问频率模型 `score = sum(1 / (1 + time_diff)^0.3)`（`m6_tiering.py:69-81`）
- **自动提升**：
  - 温层→热层：热度 > 3.0（`_promote_warm_to_hot`，`m6_tiering.py:195-210`）
  - 冷层→温层：热度 > 1.0（`_promote_cold_to_warm`，`m6_tiering.py:177-193`）
- **自动下沉**：
  - 热层→温层：热度 < 2.0（`_demote_hot_to_warm`，`m6_tiering.py:215-234`）
  - 温层→冷层：热度 < 0.5（`_demote_warm_to_cold`，`m6_tiering.py:236-252`）
- **访问行为模拟**：demo 流程中通过 `record_access(name, count=N)` 注入不同频率的访问记录（`m6_tiering.py:376-379`），热候选对象 15-25 次访问，温候选 3-6 次，冷候选 0 次

**注意事项：**
- 演示流程中的访问行为是程序化模拟（`record_access` 批量注入时间戳），而非真实用户请求触发的数据读取。但热度计算和迁移决策机制本身是真实的自动化逻辑，非静态配置或人工干预
- 采用缓存模型（数据在多层同时存在），而非互斥模型（数据只在一层）。这意味着 "迁移" 实际是 "复制"，源层数据不删除

### 6b. 展示冷热数据迁移过程连续、可观测，展示迁移事件内容，包含时间戳、触发条件及迁移前后层级信息

**结论：已满足**

代码实现情况：
- 每次迁移操作生成事件记录，包含完整信息（`m6_tiering.py:184-189` 等）：
  - `ts`：时间戳（HH:MM:SS 格式）
  - `dir`：方向（↑PROMOTE 或 ↓DEMOTE）
  - `obj`：对象名称
  - `from`/`to`：迁移前后层级（如 "温层(SSD)" → "热层(DRAM)+温层"）
  - `reason`：触发条件（如 "热度3.5>阈值3.0 (缓存提升)"）
- 事件通过 SSE 实时推送到前端（`m6_tiering.py:573-598`），前端实时渲染迁移事件列表
- 最多保留 30 条最近事件，最新事件高亮动画显示
- 前端颜色编码区分提升（绿色）和下沉（蓝色）操作

### 6c. 冷数据下沉至容量层后自动触发备份或快照生成，展示备份对象数量、耗时及生成结果；后续访问中系统自动识别热度变化并完成数据回迁

**结论：部分满足**

已实现的部分：
- **自动快照触发**：步骤 3 中 `warm→cold` 降级完成后，步骤 4 调用 `_create_snapshot(demoted)` 自动创建快照（`m6_tiering.py:399-400`）
- **快照内容完整**：快照文件（JSON）包含快照名称、时间戳、对象数量、每个对象的大小和哈希（`m6_tiering.py:254-291`）
- **快照指标展示**：前端展示快照名称、对象数量、耗时；点击可展开查看所有备份对象的详细列表（`m6_tiering.js:348-385`）
- **数据回迁**：步骤 5 对部分冷数据重新访问后，自动触发 `cold→warm` 提升（`m6_tiering.py:405-411`）

**存在的差距：**
1. **快照触发不是严格自动化**：快照创建是在演示流程步骤 4 中显式调用 `_create_snapshot(demoted)`，并非由 `_demote_warm_to_cold` 方法内部自动触发。从代码看，`_demote_warm_to_cold`（`m6_tiering.py:236-252`）本身不调用快照逻辑，快照依赖演示流程的步骤编排。要求 "自动触发备份或快照生成" 暗示应在降级操作完成时自动触发，而非由外部流程显式调用
2. **快照仅记录元数据**：快照文件仅保存对象的 size 和 hash，未保存实际数据内容。这是元数据快照而非数据备份，严格来说不满足 "备份" 的完整含义
3. **快照未落盘到持久存储**：快照文件保存在本地文件系统 `~/ceph-web/data/` 目录下（`m6_tiering.py:274`），而非保存到 Ceph 集群或其他可靠存储中。虽然文件确实写入了磁盘，但与第 4 项要求中提到的 "快照未落盘的演示视为无效" 的标准对比，当前快照实质上只是 JSON 元数据记录文件

### 6d. 依赖静态数据或人工干预完成冷热数据识别、冷热迁移、备份行为的演示视为无效

**结论：已满足**

代码实现情况：
- 冷热识别完全基于计算的热度分数，非静态标签（`calculate_heat_score`，`m6_tiering.py:69-81`）
- 迁移决策基于阈值自动判定（热度与 `THRESHOLD_HOT`/`THRESHOLD_WARM`/`DEMOTE_HOT`/`DEMOTE_WARM` 比较）
- 整个演示流程一键启动（`start_demo`），无需人工干预单个对象的迁移
- 步骤 5-6 演示了持续的热度变化检测和自动回迁能力

### 风险提示

1. **M5 单节点回退风险**（`m5_perf.py:346-348`）：当远程节点启动失败时，代码使用空列表并标记为 `single` 模式。建议在 UI 上明确标注当前是双节点还是单节点模式运行
2. **M5 RDMA 采集**：`get_rdma_stats()` 读取 `/sys/class/infiniband/` 计数器，若无 InfiniBand 设备则返回 `None`。部署环境需确保 RDMA 硬件可用
3. **M6 缓存模型与迁移语义**：当前实现为缓存模式（数据多层共存），前端展示的 "迁移" 实际为 "复制"。评审时需确认这一设计是否满足 "数据提升与下沉" 的语义预期
