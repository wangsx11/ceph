# 性能指标拆分与 performances 目录需求说明

## 1. 背景

当前性能指标集中记录在 `docs/性能要求.md` 中，现有测试脚本集中放置在 `native_rdma/tests/performance/` 下。后续希望将每个性能指标拆成独立的测试交付单元，便于逐项阅读、执行、产出报告和验收。

本轮只整理需求文档，不实现具体测试脚本，不迁移现有脚本。 

## 2. 目标目录

在仓库根目录创建 `performances/`，该目录与 `native_rdma/` 同级：

```text
ceph-web/
├── native_rdma/
├── performances/
│   ├── PF-1/
│   ├── PF-2/
│   ├── PF-3/
│   └── ...
└── docs/
```

每个性能指标对应一个独立目录，编号从 `PF-1` 开始连续递增。编号与当前 `docs/性能要求.md` 的 1 到 9 项保持一致。

## 3. 单个 PF 目录文件要求

每个 `performances/PF-N/` 目录至少包含以下文件：

```text
performances/PF-N/
├── PF-N.md
├── run.sh
├── run.py
└── summary.md
```

### 3.1 `PF-N.md`

该文件描述单个性能点的测试要求和测试方案，必须包含：

- 性能点名称。
- 来源指标，例如来自 `docs/性能要求.md` 的第几条。
- 功能点说明。
- 指标要求和通过阈值。
- 测试口径，明确统计哪些时间、吞吐、样本或带宽，不统计哪些内容。
- 交互流程，包括启动环境、设置参数、执行脚本、查看结果。
- 脚本入口，固定指向本目录下的 `run.sh` 和 `run.py`。
- 输出文件规则，固定说明本次运行结果直接写入当前 `performances/PF-N/` 目录。

建议结构参考：

```markdown
# PF-N 性能点名称测试说明

## 功能点

## 指标要求

## 测试方案

## 交互

## 实现

### 当前统计口径

### 脚本入口

## 命令
```

### 3.2 `run.sh`

`run.sh` 是该性能点的 Bash 入口，职责是：

- 定位仓库根目录和当前 `PF-N` 目录。
- 设置默认环境变量。
- 确认本次运行的输出文件位置。
- 调用 `run.py`。
- 将退出码传递给调用方。

后续实现时，`run.sh` 应尽量只做环境准备和入口封装，核心测试逻辑放在 `run.py`。

### 3.3 `run.py`

`run.py` 是该性能点的核心测试代码，职责是：

- 读取环境变量或命令行参数。
- 检查依赖条件，例如数据面 UDS、控制面 HTTP、目标二进制是否存在。
- 执行 warmup 和 measured 测试。
- 采集原始输出。
- 计算指标值、阈值和 PASS/FAIL。
- 在当前 `performances/PF-N/` 目录下生成或更新 `summary.md`。
- 如该指标需要保留机器可读原始数据，可在当前目录下生成 `raw.json`、`raw.csv` 等辅助文件。

### 3.4 `summary.md`

`summary.md` 是该性能点的汇总结果文件，作为该指标的最终结果文档：

- `performances/PF-N/summary.md`：作为该性能点的最终结果文档。

后续实现时，`run.py` 每次执行后直接更新当前目录下的 `summary.md`。本需求不引入独立的 `artifacts/` 目录，也不要求按时间戳保存历史运行目录。

## 4. 结果输出要求

每个性能指标的说明、执行脚本和最终结果都放在同一个目录下，建议格式：

```text
performances/
└── PF-N/
    ├── PF-N.md
    ├── run.sh
    ├── run.py
    ├── summary.md
    ├── raw.json      # 可选
    └── raw.csv       # 可选
```

`summary.md` 是必须文件，用于记录该指标的最终结果。`raw.json`、`raw.csv` 只作为辅助文件存在：

- 如果该性能点存在多样本或表格型输出，可以生成 `raw.csv`。
- 如果该性能点需要保留机器可读结果，可以生成 `raw.json`。
- 如果不需要原始辅助文件，应在 `summary.md` 中只保留人工可读汇总。

`summary.md` 至少包含：

- 运行结果。
- 指标要求。
- 关键统计值。
- 结果文件所在目录，即当前 `performances/PF-N/` 目录。
- 原始 JSON 路径，如果生成了 `raw.json`。
- 原始 CSV 路径，如果生成了 `raw.csv`。
- 统计口径说明。
- `PASS` 或 `FAIL` 结论。

示例结构：

```markdown
# PF-N Summary

- Metric: 性能点名称
- Samples: 30/30
- Success Rate: 100.00%
- Key Result: xxx
- Threshold: xxx
- Result: PASS

口径：
- xxx = ...
- 不包含 ...

Result Dir: /path/to/performances/PF-N
Raw JSON: /path/to/performances/PF-N/raw.json
Raw CSV: /path/to/performances/PF-N/raw.csv
```

## 6. 各 PF 文档应覆盖的测试口径

### PF-1 RDMA 分布式通讯能力

- 默认对象大小：1KB。
- 核心统计：`ops_per_sec`、业务载荷带宽、链路利用率。
- 阈值：吞吐量 >= 1,000,000 ops/s（1KB 对象场景）；带宽利用率 >= 50%（大对象场景，对象大小不限定 1KB）。
- 1KB 小对象场景下 QPS 与链路利用率无法同时达成，最终采用分项验收：QPS 指标在 1KB 场景下验收，带宽利用率在大对象场景下验收。

### PF-2 对象传输时延

- 默认样本规模：至少 100,000 个 1KB 对象。
- 核心统计：平均时延、P50、P99、P99.9、最大时延、成功样本数。
- 阈值：平均时延 <= 50us，P99 <= 100us。
- 口径应说明是否包含控制面、HTTP、脚本启动和 warmup 时间。建议只统计数据面热路径。

### PF-3 QoS 优先级

- 默认事件规模：高优先级 2500 个，低优先级 2500 个。
- 核心统计：高优先级吞吐、低优先级吞吐、处理效率提升比例。
- 阈值：高优先级相对低优先级提升 >= 22%。
- 口径应明确提升比例公式，例如 `(hi - lo) / lo * 100%`。

### PF-4 对象数据聚合传输

- 场景 A：100 个 1KB 对象，1000 批次。
- 场景 B：1000 个 1KB 对象，100 批次。
- 不同批次之间串行执行，前一批次完成后再发下一批次。
- 核心统计：两个场景的总耗时、成功批次数、失败批次数。
- 阈值：场景 A <= 200ms，场景 B <= 100ms。

### PF-5 批处理吞吐

- 默认对象大小：1KB。
- 默认批次：覆盖 1000 批次和 100 批次两类场景。
- 核心统计：MB/s、ops/s、失败数、降级数。
- 阈值：传输速度 >= 700MB/s。

### PF-6 多级存储读写

- 核心统计：写入 GB/s、读取 GB/s、读命中率或有效响应字节比例。
- 阈值：写入 >= 10GB/s，读取 >= 20GB/s。
- 口径应明确使用真实字节计数，避免用 `ops/s * 假定对象大小` 在 miss 或短响应场景下高估吞吐。
- 需要在文档中说明运行前提，例如 1MB payload 场景可能要求数据面启动时设置足够大的 slab slot。

### PF-7 仿真引擎定期备份存储能力

- 存储前提：必须能确认测试路径位于 3+1 RAID5 系统上。
- 默认请求大小：4KB。
- 核心统计：写入延迟 P50、P95、P99、P999、最大延迟、成功请求数。
- 阈值：4KB 写入请求 P999 延迟 <= 1ms。
- 口径应明确随机写还是顺序写、是否使用 direct I/O、是否 fsync、队列深度、并发线程数和测试时长。
- 当前环境可看到 MR9560-8i RAID 控制器暴露的块设备，但需要通过 RAID 控制器工具或运维信息确认其 RAID level 和成员盘数量；未确认前只能作为当前存储路径写入延迟测试，不能作为严格的 3+1 RAID5 验收。

### PF-8 仿真引擎运行能力

- 默认实体数：100,000。
- 默认事件数：1,000,000。
- 默认节点数要求：指标写明 4 个节点；当前硬件事实是双节点，需要在文档中标明后续实现是模拟 4 节点、扩展到 4 节点，还是按双节点降级演示。
- 核心统计：仿真时间、墙钟时间、speedup、events/s。
- 阈值：`speedup >= 1.0`。

### PF-9 内存池化能力

- 默认对象大小：1KB。
- 场景一：启用内存池后的性能损失 <= 5%，内存节省 >= 7%。
- 场景二：单节点多线程高并发分配/释放，吞吐量提升 >= 20%。
- 核心统计：overhead_pct、savings_pct、scale_gain_pct、线程数、总操作数。

## 7. 统一运行约定

后续实现每个 PF 时建议支持以下统一参数：

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `OUT_DIR` | 环境变量 | 当前 `performances/PF-N` 目录 | 本指标输出目录 |
| `UDS` | 环境变量 | `/tmp/native_rdma-dp.sock` | 数据面 Unix domain socket |
| `CTRL_URL` | 环境变量 | `http://127.0.0.1:5000` | 控制面 HTTP 地址 |
| `DUR` | 环境变量 | 按 PF 定义 | 单轮压测持续时间 |
| `THREADS` | 环境变量 | 按 PF 定义 | 并发线程数 |
| `WARMUP_RUNS` | 环境变量 | 按 PF 定义 | warmup 轮次 |
| `MEASURED_RUNS` | 环境变量 | 按 PF 定义 | 正式统计轮次 |
| `REQUIRE_PEER` | 环境变量 | `1` | 是否要求跨节点成功，避免本地降级数据污染结果 |

所有脚本应支持：

```bash
cd performances/PF-N
bash run.sh
```

## 8. 与现有脚本的关系

`native_rdma/tests/performance/` 下已有脚本可作为实现参考，但后续 `performances/PF-N/` 应成为面向验收的主入口。

迁移时建议遵循：

- 保留现有脚本，避免破坏当前验证入口。
- 每个 `PF-N/run.py` 可以复用现有脚本逻辑，也可以直接调用 `native_rdma/build/bin/nr_bench` 等二进制。
- 新目录的输出统一写入当前 `performances/PF-N/` 目录。
- 新目录的 `summary.md` 使用统一的人类可读格式。
- 如继续保留 `native_rdma/tests/run_all_performance.sh`，可在后续改为调用 `performances/PF-*/run.sh`。

## 9. 待确认事项

后续正式实现前建议确认以下细节：

1. `performances/` 是否确定使用复数命名，并固定为与 `native_rdma/` 同级。
2. 每个 `summary.md` 是只作为模板提交，还是每次运行后覆盖为最近一次结果。
3. `PF-1` 的 1KB 小对象吞吐和 50% 链路利用率是否必须同时满足。
4. `PF-7` 的 3+1 RAID5 拓扑如何确认，是否能安装或使用 RAID 控制器查询工具。
5. `PF-8` 的 4 节点指标在当前双节点硬件上如何验收。
6. `PF-6` 的全闪存阵列读写指标是否以当前分级存储实现测量，还是需要单独接入真实全闪存路径。
7. 是否需要增加一个总入口，例如 `performances/run_all.sh`，用于批量执行所有 `PF-*` 并生成总览报告。
