# 功能测试视频展示文案

本文档用于后续录制功能要求展示视频。讲解顺序按照 `docs/功能要求.md` 的三大模块展开：多级异构的高效能存储模块、RDMA 分布式仿真计算模块、一致性总线内存池化仿真计算模块。当前阶段展示功能测试总览、测试框架、多级异构存储模块的 FN-1 到 FN-6、RDMA 模块 FN-1 到 FN-5，以及内存池模块 FN-1 到 FN-6。

## 开场说明

本视频展示的是 native RDMA 分布式共享数据系统的功能验证结果。系统的数据面由 C++ 实现，控制面和页面只负责触发与展示。功能测试不是通过 UI mock 或脚本制造结果，而是通过 `functions/` 目录下的独立验收脚本，直接调用数据面 Unix Domain Socket RPC，采集原始响应、summary 和日志。

本轮功能测试统一从 `functions/run_all.sh` 或单个 `functions/<module>/FN-N/run.sh` 入口执行。每个功能点都包含说明文档、执行脚本、最近一次 `summary.md`、机器可读 `raw.json` 和 `logs/` 过程日志。脚本遇到数据面不可达、peer 不在线或硬件前提不满足时，不会生成假 PASS，而是返回 `SKIP` 或 `FAIL`；历史 `WAIVED` 口径已不再用于 RDMA FN-4。

## 功能测试框架

功能测试目录分为三个模块：

- `functions/storage/`：对应多级异构的高效能存储模块，覆盖统一存储接口、冷热分离、预取、压缩去重、I/O 调度和运行中采集。
- `functions/rdma/`：对应 RDMA 分布式仿真计算模块，覆盖统一通信层、聚合传输、QoS、GPU Direct RDMA 和路由负载均衡。
- `functions/mempool/`：对应一致性总线内存池化仿真计算模块，覆盖 RDMA 远程内存访问、内存池 API、统一命名、自适应迁移、隔离和高可靠。

每个功能点都按同一套执行结构组织：

```text
functions/<module>/FN-N/
├── FN-N.md
├── run.sh
├── run.py
├── summary.md
├── raw.json
└── logs/
```

其中 `run.sh` 是 Bash 入口，`run.py` 调用公共测试框架，公共逻辑位于 `functions/common/`。脚本直接走 C++ 数据面 UDS，例如 `RPC_KV_PUT`、`RPC_KV_GET`、`RPC_TIER_DEMOTE`、`RPC_TIER_STATS`。每次运行都会覆盖该功能点的最近结果，并把完整过程保存在 `logs/` 中，便于复核。

## RDMA FN-1 RDMA 与 TCP/IP 统一通信层

### 我的理解

这一项验证的是分布式通信层的基础能力：数据面需要创建 RDMA RC QP，通过 TCP/OOB 通道交换 peer 的 QPN、slab base、rkey 等元数据，再把 QP 切到 RTS 状态。同时，系统现在新增了独立 TCP data channel，用于验证传统 TCP/IP 数据通道能承载对象复制和远端读取闭环。

完整验收要求 xfusion3 和 xfusion4 双节点在线。仅看到历史日志里出现过 `TcpFallback connected` 或 `OOB exchanged`，不能证明当前通信层仍在线。

### 我是怎么测试的

FN-1 使用 `functions/rdma/FN-1/run.sh` 执行。脚本调用 `RPC_CLUSTER_STATUS`，读取 `native_rdma/logs/dp_<role>.log`，并只检查最近一次 `native_rdma_dp starting` 之后的启动段。

通过条件包括：

- 最近启动段包含 `created ... QPs`。
- 最近启动段包含 `TcpFallback listen` 或 `TcpFallback connected`。
- 最近启动段包含 `OOB exchanged`。
- 默认 `REQUIRE_PEER=1` 时，`RPC_CLUSTER_STATUS.peer_alive=true`，且 `peer_num_qp`、`peer_slab_base`、`peer_slab_rkey` 有效。
- `RPC_CLUSTER_STATUS.transport=tcp` 且 `async_repl=false`，证明普通 PUT 路径已显式切换到 TCP，同步 RDMA 时延可对比。
- `RPC_CLUSTER_STATUS.tcp_data_ready=true`。
- 普通 `RPC_KV_PUT` 返回 `transport=tcp` 且 `degraded=false`。
- `RPC_TCP_GET_PEER` 从 peer 读回同一 value。
- 脚本额外执行 `RPC_KV_PUT_RDMA` 和普通 `RPC_KV_PUT` 多个样本，汇总 RDMA/TCP 同步复制时延的 avg、p50、p95、min、max。展示单位统一为 `us`，`raw.json` 保留 `ns` 原始值。

如果 peer 不在线，当前环境无法访问 UDS，或 TCP 数据闭环失败，脚本不会把历史日志制造成 PASS。

## RDMA FN-2 聚合数据传输

### 我的理解

这一项要求系统支持小规模数据包或多个通信流的聚合传输。当前项目的数据面有两层相关实现：一层是 `BatchAggregator` 线程初始化，面向 linked-list RDMA WR 聚合；另一层是 `RPC_KV_PUT_BATCH`，把多个小对象放进同一个 UDS RPC，在数据面内批量解析、批量 slab/tier 处理，并在 peer 在线时逐项执行 RDMA WRITE。

## RDMA FN-3 流量优先级机制

## RDMA FN-4 CPU 与 GPU 高速直通访问

### 我的理解

这一项验证的是 GPU Direct RDMA 数据面闭环。当前硬件拓扑是 xfusion3 没有可用 NVIDIA GPU，xfusion4 有 A100/A800；因此最合适的证明方式不是让两端 GPU 互通，而是让 xfusion4 暴露由 `cudaMalloc` 分配并通过 `ibv_reg_mr` 注册的 GPU MR，xfusion3 通过 RDMA WRITE 直接写入这个 GPU MR，再由 xfusion4 使用 CUDA kernel 在 GPU 侧校验显存内容。

需要准确说明边界：CPU 负责准备测试 pattern 和提交 RDMA WR；数据 payload 由 RNIC 直接进入 xfusion4 GPU 显存；这不是 GPU 自主发起网络操作，也不是普通 CPU slab、TCP、全量 `cudaMemcpy` payload 或脚本写 JSON 冒充 GPU Direct。

### 我是怎么测试的

FN-4 使用 `functions/rdma/FN-4/run.sh` 执行。完整验收需要先检查 xfusion4 的 GPU/CUDA/RDMA/peer memory 状态，并以 GDR 模式启动双节点：

```bash
ssh xfusion4 'hostname; nvidia-smi; nvidia-smi topo -m; lsmod | egrep "nvidia_peermem|nv_peer_mem"; /usr/local/cuda/bin/nvcc --version || nvcc --version || true; ibv_devinfo | head -80'
cd native_rdma
LOCAL_HOST=xfusion3 NR_GDR_ENABLE=1 NR_TRANSPORT=rdma NR_ASYNC_REPL=0 bash start.sh
cd ..
REQUIRE_PEER=1 bash functions/rdma/FN-4/run.sh
```

如果 peer memory 模块未加载，先在 `xfusion4` 上手动执行 `sudo modprobe nvidia-peermem`。脚本不允许用 CPU buffer、TCP 或直接写 JSON 代替 GPU Direct 证据。

脚本通过条件包括：

- xfusion4 硬件检查证明 NVIDIA GPU、CUDA、`nvidia_peermem`/`nv_peer_mem` 和 `mlx5_0` 可用。
- A 端 `RPC_CLUSTER_STATUS.peer_alive=true` 且 `transport=rdma`。
- A 端 `RPC_GDR_STATUS` 证明 peer GPU MR 的 `base/rkey/len` 有效。

## Mempool FN-1 RDMA 语义远程内存访问与零拷贝

### 我的理解

这一项验证的是一致性总线内存池化模块的底层远程内存访问能力。完整证据不能只看 HTTP 或本地 `RPC_KV_PUT` 成功，也不能用 peer 离线时的本地 degraded 写入冒充；必须证明对象写入走 C++ 数据面的 RDMA WRITE，目标地址来自 peer 通过 OOB 交换得到的 slab base/rkey，并且写入后能从 peer 端读回同一对象。

当前实现中，A/B 两端启动时都会把本地 slab 注册成 RDMA MR。OOB 交换会把 `peer_slab_base`、`peer_slab_len`、`peer_slab_rkey` 和 QP 信息交给对端；`RPC_KV_PUT_RDMA` 在 peer 在线时调用 `RdmaCore::post_write`，把本地 slab 槽位内容写到 `peer_slab_base + offset`。peer 读回使用 TCP data channel 触发 peer 本地读取，只作为远端内容校验，不把读回通道描述成 RDMA READ。

## Mempool FN-6 内存池高可靠机制

## Storage FN-2 多层感知、冷热分离与调度

## Storage FN-3 文件访问多策略预取

### 我的理解

这一项验证的是存储模块是否能根据访问局部性提前加载后续对象。它不应只停留在“预测接口返回了一个 key”，而要证明数据面根据预测结果把低层对象提前提升到 DRAM，随后真正读取该对象时能直接命中本地内存。

当前实现包含两种策略。第一种是 stride 预取：连续访问带数字后缀且步长一致的 key 后，预测后续顺序 key。第二种是 Markov-1 预取：记录对象之间的高频转移关系，例如反复访问 `A -> B` 后，在访问 `A` 时预测 `B`。

为了避免测试脚本制造结果，`RPC_PREFETCH_STATS` 只负责查询预测候选和统计，不会因为查询本身增加策略命中计数。真实证据来自 `RPC_KV_GET` 数据面路径：GET 触发预取候选，数据面调用 `TierEngine::promote` 将 NVMe/HDD 对象加载回 DRAM，并通过 `prefetch_loaded` 和 `prefetch_hits` 记录实际加载和后续命中。

## Storage FN-4 可配置压缩与去重

## Storage FN-6 仿真数据运行中采集

### 我的理解

这一项验证的是仿真运行时的数据流能否被及时捕获下来。它不是只要求仿真跑完后有一个总数，而是要求对象属性变化和对象间交互事件都进入数据面采集链路，并最终落到可复核的 WAL 文件。

当前实现中，`SimEngine` 在 `RPC_SIM_RUN` 运行期间按采样比例把事件推入 `SimCapture`。对象属性事件使用 `type=1 ObjectAttr`，交互事件使用 `type=2 InteractionEvent`。`SimCapture` 在 C++ 数据面内维护采集缓冲，并由后台线程批量写入 WAL 文件。`RPC_SIM_CAPTURE_STATS` 暴露 push、flush、drop、两类事件计数以及 `wal_path`。

### 我是怎么测试的

FN-6 使用 `functions/storage/FN-6/run.sh` 执行。脚本直连 C++ 数据面 UDS。

测试分为四步：

第一步，调用 `RPC_SIM_CAPTURE_RESET` 清空采集计数和当前 WAL，避免历史事件影响本次结果。

第二步，调用 `RPC_SIM_RUN` 运行轻量仿真，参数包含 `entities=1000`、`events=2000`、`threads=2` 和 `capture_every_n=10`。通过条件是 RPC 返回成功，并且 `captured_events>0`。

第三步，等待后台 flush 后调用 `RPC_SIM_CAPTURE_STATS`。通过条件是 `pushed_events`、`flushed_events`、`pushed_bytes`、`flushed_bytes` 都大于 0，`dropped_events=0`，并且 `object_attr_events` 和 `interaction_events` 都大于 0。

第四步，脚本打开 `wal_path` 对应的 WAL 文件，按 `SimEventHeader` 二进制格式解析每条记录。通过条件是 WAL 文件存在、没有截断记录、文件大小不小于 flush 统计，并且解析结果中同时包含 `type=1` 和 `type=2`。
